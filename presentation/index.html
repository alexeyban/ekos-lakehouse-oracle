The usual problem: the knowledge is spread over code, scripts, a docs site and the database, and the people who knew why are gone. Before building a lakehouse on it, someone has to say what it is.

Oracle XE 21c with the iDempiere 12 seed, in Docker2
The approach

Compile the knowledge, then let a person decide

  • EKOS observes sources without interpreting them, compiles them through deterministic passes and keeps every conclusion with its evidence in an append-only ledger.
  • No language model reads the sources. The one model call of the workflow drafts a mart from plain words — and every term it writes is resolved against the approved model, or asked back.
  • Decisions are a person's, and bound to what was shown: a sign-off carries a digest; when a fact changes, the sign-off turns stale by itself.
  • EKOS Lakehouse turns the approved model into an Iceberg lakehouse: extraction, dbt silver and gold, Dagster.

Step 1 — analyse

Code, docs and the live catalog in one ledger

  • Java declarations and the application model; Oracle SQL and PL/SQL; migration scripts as schema history; docs with their tickets; the live catalog read inside a read-only transaction.
  • 446 places where code and database disagree, each with its evidence.
  • Per table: how rows are updated and deleted.
  • Pipeline: build 16 s · recover 4 min · commit 8 min · 0 model calls.

Step 3 — review and sign-off

A person signs what they were shown

  • Six subjects: scope, PII, write behaviour, glossary, conflicts, identity.
  • A sign-off is bound to a digest. Adding a column in Oracle turned the PII sign-off stale, naming the column.
  • 4 of 6 signed; 195 code ↔ database conflicts wait for a person — the software shows them, it does not decide them.
Steps 4–7 stay behind this gate7
Step 4 — requirements

The one model call, and nothing invented

  • "Number of completed sales orders per customer and month": local llama3 drafts the mart's header.
  • EKOS resolves every term against the approved model — columns, join paths along declared keys, filters.
  • What does not resolve is a question for the operator, never fed back to the model.
  • Approval records the requirement's digest.
4 requirements approved; one model draft needed nine answers8
Step 5 — extraction

How each table lands, with the evidence

  • Incremental on UPDATED where the code keeps it; full where some code skips it.
  • Deletes found by a bucketed key diff, with a mass-delete guard; purged rows kept.
  • Step 3's scope and PII masks applied; a number no Iceberg type can hold is refused, never rounded.
  • The operator changes what they disagree with, with a reason, and approves the plan's digest.
715 incremental · 134 full · 1 refused · 53 out of scope · 1 masked column9

What is guaranteed

Measured, not promised

  • No row values in the ledger: 228 text values sampled from 36 business columns — 0 in anything read from the database.
  • No model call outside step 4: every recorded run log ends with its count — 0 in steps 1, 2, 5 and 7.
  • Every number traceable: run logs per command; the pipeline is a git repository; approvals are ledger facts.
  • The plan's release gates: 8 met, 2 partial, 2 blockers — open conflicts for a person, and three delete scenarios still to plant on the testbed.
docs/results/exit-report.md11
Not done, honestly

What this demo does not show

  • A complete step-3 sign-off: 195 conflicts and one identity match are a person's work.
  • The full 849-table load: a 15 GB laptop ran a 165-table subset.
  • Cascade, keyless and permissions-loss deletes on the testbed (designed and classified, not planted).
  • CDC with Debezium: optional, built only when an operator asks for it.
